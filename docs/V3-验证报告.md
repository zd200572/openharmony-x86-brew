# V3 验证报告:真实源码编译路径(容器即构建机)

> 2026-10-03 · 前置:V0(工具链冒烟)/ V1(最小 rootfs)/ V2(brew 引导链)/ CI(GitHub Actions 全绿)均已完成,见各自报告与 `handoff.md`

## 一、目标与结论

**目标**:打通"容器内真实源码编译"路径——不依赖宿主机交叉编译,在 OHOS x86_64 rootfs 容器内部,用 brew formula 驱动上游源码(autotools/configure 类)构建,并产出 x86_64_ohos bottle。

**结论:全链路打通。** 容器内 `ohos-clang`(Alpine clang 15.0.7 + OHOS sysroot)可编译/链接/运行 C 与 C++(libc++);brew 以 `--build-bottle` 从上游 zlib-1.3.1 源码完成构建;`brew test` 通过;产出 `zlib-1.3.1.x86_64_ohos.bottle.tar.gz`(bottle 标签确认为 `x86_64_ohos`);卸载后 pour 该 bottle 成功且再测通过;docker 镜像容器内端到端复验全绿。

## 二、方案:Alpine clang + OHOS sysroot

- 编译器:容器内已有 Alpine musl 原生 clang 15.0.7(SDK 的 clang 是 glibc 二进制,进不了 musl 容器)
- sysroot:OHOS SDK `native/sysroot`(60MB,usr/include + usr/lib/{aarch64,arm,x86_64}-linux-ohos)整体拷入 `/opt/ohos-sysroot`
- 链接器/工具:Alpine `binutils 2.44`(ld/ar/as/nm/ranlib/strip,需 `jansson` 运行库)
- wrapper:`/opt/ohos-clang/bin/ohos-clang{,++}`(软链到 `/bin`),标志位照抄 OHOS SDK wrapper

### 关键设计:wrapper 完全自管链接

实测发现 **Alpine 构建的 LLVM 不含 OHOS 工具链分支**(libLLVM 连 ohos 三元组字符串都没有;OHOS SDK 的 clang 是其自研 llvm-project fork)。alpine clang 对 `-target x86_64-linux-ohos` 走默认 generic Linux 路径:glibc dynamic-linker、`crtbeginS.o`、`-lgcc`、`-lssp_nonshared` 全是错的。

因此 wrapper 两层接管:

1. **编译期**:`-target x86_64-linux-ohos --sysroot=/opt/ohos-sysroot -D__MUSL__ -isystem /opt/ohos-sysroot/usr/include/x86_64-linux-ohos`
   (multilib 头目录必须显式给:`bits/alltypes.h` 在 `usr/include/x86_64-linux-ohos/bits/`,alpine driver 不会自动加)
2. **链接期**:`-nostdlib` + 显式排 crt(`Scrt1.o crti.o <用户对象> crtn.o`,均取自 sysroot)+ `-L sysroot` + `-lc`(C++)/`-lc++ -lc`(C++,libc++ 在后)+ `-no-pie` + `-Wl,-dynamic-linker=/lib/ld-musl-x86_64.so.1`(覆盖 driver 默认的 glibc loader)+ `-Wl,-rpath-link,/lib`(GNU ld 解析**传递 NEEDED** 不认 `-L`,`libruby.so` 依赖的 `libz.so` 在 /lib)
   - 编译/链接/`-shared` 三种模式按参数自动分流;`-shared` 不排 exe crt

### C++(libc++)三件套

| 件 | 来源 | 坑 |
|---|---|---|
| 头(基础) | SDK `llvm/include/c++/v1` | sysroot 自身不带 c++ 头 |
| 头(覆盖层) | OHOS prebuilts `libcxx-ndk/include/libcxx-ohos/include/c++/v1/{__config,__config_site}` | 缺 `__config_site` 直接编不过;已固化为仓库资产 `v3/assets/`(CI 无 OHOS 源码树时兜底) |
| 库 | rootfs `/lib64/libc++_shared.so` | 其导出命名空间为 `__n1`,与覆盖层 `__config_site` 的 `_LIBCPP_ABI_NAMESPACE __n1` 一致;**`/lib64/chipset-sdk-sp/libc++.so` 是 `__h` 命名空间(系统版),与 NDK 头不匹配,勿用**(实测 undefined reference) |

## 三、容器补件清单(全部 Alpine v3.22 main,musl 原生)

| 包 | 解决的问题 |
|---|---|
| `clang15-headers` | clang 资源目录(缺失则 `stdio.h file not found`;Alpine 把资源头拆成独立包) |
| `binutils`(+`jansson`) | ld/ar/as/nm/ranlib/strip(容器原本无任何链接器;ld 链接 libjansson) |
| `make` | brew formula 构建必需(容器原本无 make) |
| `tar`(+`acl-libs`) | **GNU tar 是 brew bottle 的硬需求**(brew bottle 用 `--hard-dereference`,toybox tar 无此选项) |

拷贝纪律:**逐条目 `cp -a --remove-destination`**(见踩坑 #25——`cp -a dir/.` 穿过 `/usr/bin→../bin` 软链后与 toybox 应用小程序软链相撞会覆盖 `/bin/toybox` 本体,全容器 ls/grep/sed 尽毁;脚本内置 toybox 完好性自检与从 v1 基底 tar 的自愈)。

## 四、brew 侧改造(全部归档进幂等重放机制)

| 改造 | 位置 | 说明 |
|---|---|---|
| Gemfile.lock PLATFORMS += `x86_64-linux-ohos` / `x86_64-linux-musl` | `v2/apply-brew-patches.sh`(sed) | 原白名单只有 arm64 系,本地平台直接被拒 |
| `bundle lock --add-platform x86_64-linux-{ohos,musl}` | 同上(chroot 执行,`.x86-lock-done` 标记防重复联网) | 冻结模式要求 lock 对声明平台解析完整(prism 等原生 gem 有平台变体) |
| `SSL_CERT_FILE=/etc/ssl/certs/cacert.pem` + `~/.gemrc` + `~/.bundle/config` | `v3/stage-v3.sh` | ruby 的 OpenSSL 编译期 CA 路径(OHOS SDK)容器内不存在;bundle 子进程不继承 SSL_CERT_FILE,配置文件双保险 |
| rbconfig 工具链容器化 | `v3/stage-v3.sh`(sed) | ruby 交叉编译时烤进 rbconfig 的 CC/CXX/AR/LD 等全是宿主机 SDK 路径,容器内不存在 → gem 原生扩展(prism/bigdecimal 等)全灭;重定向到 `ohos-clang`/binutils 后 gem 生态解锁(Tier-2 前提) |
| `HOMEBREW_DEVELOPER=1` 烘焙 brew.env | `v3/stage-v3.sh` | bottle pour(本地 .bottle.tar.gz)被 `forbid_packages_from_paths`(默认 true)拦截;`HOMEBREW_INTERNAL_ALLOW_PACKAGES_FROM_PATHS` 会被 brew 入口环境白名单洗掉,实测只有 `HOMEBREW_DEVELOPER` 能穿透并翻转默认 |
| `brew trust ohos/local` | `v3/verify-v3.sh` | Harmonybrew tap 信任机制,pour 时触发 |

## 七、已知限制与下一步

1. **autotools/libtool 包未验**:zlib 是自编 configure;xz/libtool 类(需 config.guess 识别三元组)待验——容器内可运行编译产物,configure 的 run-test 天然通过,预期顺畅
